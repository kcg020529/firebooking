## 2. Day 1 안건과 실제 결정

Day 1에 올렸던 안건과, 프로젝트를 진행하며 실제로 어떻게 정해졌는지.

### 사람 · 계정

| # | 안건 | 결정 |
|---|---|---|
| 1 | **Vercel 계정 소유자** | kcg020529 단독 소유(개인 Hobby 계정). B·C는 Vercel 계정 불필요 — 배포 URL은 공개, 로그·env는 필요할 때만 A가 공유 |
| 1-1 | **GitHub 저장소 공개 여부** | **public 전환.** Hobby 플랜은 프라이빗 저장소에서 소유자 아닌 사람의 push를 배포 차단함(C의 `feat/llm-security` 브랜치가 "Deployment Blocked"로 막혔던 원인). public은 Hobby에서도 컨트리뷰터 프리뷰 배포를 지원. 전환 전 전체 git 히스토리를 실제 키 패턴으로 스캔해 유출 0건 확인 |
| 2 | **Supabase 프로젝트 소유자** | kcg020529. Vercel과 같은 사람으로 통일. 스키마·RLS·Cron 적용과 `SERVICE_ROLE_KEY` 관리를 A가 전담 |
| 3 | **DeepSeek 크레딧 결제자** | 별도 정산 없이 종료. 초기에는 Anthropic 키를 쓰려다 발급이 막혀 DeepSeek으로 전환(`f8200f2`) |
| 4 | **GitHub 브랜치 보호 규칙** | **켜지 않음.** 저장소 설정 대신 `CLAUDE.md`의 "`main` 직접 push 금지" 규칙과 PR 절차로만 운영. 3인·2주 규모에서 설정 승인 대기 비용이 더 크다고 판단 |

### 협업 방식

| # | 안건 | 결정 |
|---|---|---|
| 1 | **PR 머지 방식** | **Merge commit.** 브랜치별 작업 과정을 그대로 남겨 두는 쪽을 택함. 보고서에서 "언제 무엇을 고쳤는가"를 커밋 단위로 인용해야 해서 squash로 뭉치면 근거가 사라짐 |
| 2 | **PR 리뷰 배정** | 고정 배정 없이 운영. 실제로는 **리뷰 승인 절차 없이 작성자가 직접 머지**하는 형태가 됐다. 기간상 리뷰 대기 비용이 커서 그렇게 흘렀고, 대신 PR 본문에 변경 이유·검증 결과를 남기는 것으로 대체함 |

### 프로젝트 내용

| # | 안건 | 결정 |
|---|---|---|
| 1 | **주제 이름** | 골프 예약 사이트(필드·스크린) + 로그 보안 서비스 |
| 2 | **시연 계정** | 관리자 1개 + 일반 계정으로 운영. 역할 승격은 Supabase SQL Editor에서만 수동으로 하고(스스로 권한 상승 불가), 계정 정보는 저장소에 남기지 않음 |
